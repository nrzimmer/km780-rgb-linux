The byte 0x07 is not a magic number

The abandoned repo legonigel/KM780-RGB-Linux-Driver calls byte 0 KM_START_CHAR, a "manufacturer magic character". It is the HID Report ID — the same 7 that makes up wValue = 0x0307, where 0x03 is the report type FEATURE and 0x07 the report ID. Anyone implementing the transport that way is right by accident and wrong the moment they generalize.

The transaction, the way the manufacturer does it

Taken from FUN_100d8fc0. The official software does not read the ACK on the interrupt endpoint 0x83: it writes, sleeps, and reads back into the same buffer. C

  1. memset(buf, 0, 0x200); buf[0]=0x07; buf[1]=cmd
  2. HidDevice_SetFeature(h, buf, 0x108, 0) ordinal 7
  3. Sleep(10) 50 ms on the paged commands
  4. HidDevice_GetFeature(h, buf, 0x108, 0) ordinal 8
  5. Sleep(10) 100 ms on the paged commands

The abandoned repo's ACK wait works, but it loops forever if the ACK never arrives — and it is not what the manufacturer does.

bcdDevice carries the firmware version

In the device descriptor, bcdDevice = 0x0077 is FW 77. A practical consequence: lsusb reveals the keyboard's firmware version with no software at all. The firmware also carries three copies of the configuration descriptor, identical except in the endpoints' bInterval — 1, 4 and 8 — which are the UI's polling rate options.

The event channel, 0x83

8 bytes, vendor page 0xFF00. This is where the keyboard speaks on its own: the MR/M1/M2/M3 keys switch the mode and record macros with no software, so the active mode changes underneath the host.

Command space

Bit 7 set = a read, confirmed empirically across nine pairs — no longer inferred. But the evidence comes from two sources of different strength, and the difference matters when deciding what to probe:

  • Four seen answering on the wire — 0x01/0x81, 0x02/0x82, 0x09/0x89, 0x0A/0x8A. C
  • Five confirmed only in the binary — 0x05/0x85, plus 0x0B/0x8B, 0x12/0x92 and 0x15/0x95, which FUN_100db460 emits with buf[3]=0. They do not appear in the captures because that function does not run on the exercised paths. C

0x95 is the read of Changeling and did not exist in any document until this round.

write observed read observed event device→host read only in the binary never observed
Do not sweep unknown commands

That is exactly what put the keyboard into bootloader mode: some byte between 0x96 and 0xAF is not a read, despite having bit 7 set. The "bit 7 means read" convention holds for the confirmed commands, not for arbitrary bytes. Recovery exists (FWUpdate.exe + the .hex), but it depends on a Windows machine.

The prime suspect is 0x96. The confirmed read space ends at 0x95, and the next byte would be the read of 0x16 — the command that opens the session, the init's first message. The limit landing exactly there and the sweep starting to fail on the byte just above is too much of a coincidence. There is no proving which byte it was, but do not probe that one. I

The list is a floor, not the complete set. The xrefs of the SetFeature thunk give 23 send calls — it was never the 37 assumed, because the 37 push 0x108 also include the GetFeatures. Today there is a located build site for 16 of the 18 commands on the wire; only 0x07's is missing.

What found the missing ones was looking for the pair buf[0]=0x07 followed by buf[1]=cmd at consecutive offsets — that is what separates a packet's 0x07 from any old 0x07 in the code. Searching for a lone immediate drowns 0x0E in hundreds of false positives.

0x09 · LED Matrix Database

The color path. A complete update is three packets, one per channel — it is not key paging. Each packet carries 144 bytes, one per LED slot, with that channel's intensity on that LED.

Read from the author's keyboard: mode 1 has 127 slots at ff0000, and mode 2 has 122 at 00fb2f plus 5 red ones, and mode 3 has 11 distinct colors — the Wave's gradient already rasterized into the matrix. The most frequent color in mode 3 is c6010b, which is exactly one of the color stops stored in that mode's 0x0A database: the stored gradient and the matrix agree.

Which channel is R, G and B

It could not be found out from the binary: the firmware treats the three channels symmetrically — FUN_000081b8 only clamps to 1..3 and copies 144 bytes — and each one comes from a distinct 4 KB bank in the external SPI flash (0x1070, 0x2070, 0x3070). A correspondence is a convention of the LED hardware, and it came out of a hardware test: F5 (slot 45) on channel 1 only, F6 (slot 54) on channel 2 only, F7 (slot 59) on channel 3 only, all with 0xFF. C

Three things the same test settled

There is no commit. The third packet closes the update; no separate apply command. 0x09 is authoritative for static color — in the test every other key went dark, because they were sent as zero; if there were an effect or brightness layer on top, they would have stayed lit. And the read is symmetric: 0x89 returns the bytes sent and echoes the header, which confirmed that buf[2] is the mode and buf[3] the channel.

The intensity is not here

It is byte 11 of the mode payload (0x02), with values 0 to 4 — the UI's five levels. Walking through all the levels, the only byte that varies across the 12 0x02 packets is 11, in the sequence 00 00 01 02 03 04, and the 0x09 packets sent alongside keep the color intact. That is: the firmware applies the brightness; the host does not pre-multiply the color. C

Key → LED slot map

There are 132 slots used out of 144. The order is not the keyboard's physical one — it is the hardware's LED scan order, which is obvious here: neighbouring slots land in opposite corners of the keyboard. Click a key to see the slot, o HID usage e o virtual-key code.

The physical layout came from the manufacturer C

physical-matrix.json is the electrical scan matrix and is no use for drawing the keyboard — the wiring does not follow physical adjacency. The real position was in the official software's package: external/gds/…/KeyboardButtons.xml carries each key with a <POS> in x, y, width and height. There are 110 keys, the 104 from <KEY_NUM> plus the six G keys.

The 12 that are missing — MR, M1–M3, the WinLock/Brightness/Timer trio and the five multimedia ones — are not there because the official app does not let you reassign them. They were measured from the photo in Keyboard Wireframe_01232015v3.pdf, in the same package.

110 + 12 = 122, and 122 is exactly how many keys the matrix sweep counted on the hardware, by a route unrelated to this one. Two sources that never talk to each other on the same number.

Slot 126 is the numeric keypad's Enter C

The factory table calls it NumSep (from VK_SEPARATOR) and the matrix map calls it NumEnter; it was not obvious they were the same key. They are: the manufacturer's XML names the entry NUM_ENTER  VK_SEPARATOR, and the slot's HID is 0x58 — Keypad ENTER. Three sources, one key.

The codes aa and ab are the wheel

The Multimedia function range has seven codes, a5 to ab. Five now have names — Stop, Prev, Play/Pause, Next, Mute. The app's dialog offers seven options: those five plus Volume Up and Volume Down. And the volume wheel is the only control that emits no event and has no LED slot. Both ends meet. I

In the matrix, but not on the keyboard

Five slots within the 132 have no physical key on the US/ABNT layout — all with a HID usage in the international range 0x85–0x8b, and four of them with vk = 0. They are positions from JIS/ABNT layouts that the matrix addresses but the board does not expose. The remaining 12 slots (144 − 132) are addressed by no table at all and stay dark in every mode: those simply do not exist.

A dark slot does not mean a non-existent slot

This list once had ten slots. The other five went in because they came back dark in a matrix read — and that inference does not hold. Reading the real keyboard, the set of dark slots changes with the mode: in modes 1 and 2 they are the international keys, in mode 3 they are the media keys and the zones. Only one slot is dark in all three.

The matrix stores what was painted last. A dark slot only says nobody wrote a color into it. Settling this for good means writing a color into the suspect slot and looking at the keyboard.

The Linux map decodes the Windows captures

Applied to the f6 events of the 11 captures made on the other machine, the map recognises 1,535 out of 1,535 and gives back the real typing in readable text:

F I Z · M A I S · D · Backspace · C O I S A S

No coordinate captured on Windows fell outside the map collected on Linux.

Column 0 is the entire left-hand side — G1 to G6 in rows 0 to 5, then MR, M1 and M2. Nine positions, nine keys, in order. M3 does not fit there and came out at (2,6): the wiring does not follow physical adjacency.

That is also why the earlier deduction of 13 × 9 was short — column 0 was never pressed on Windows, because G keys and modes type nothing and nobody pressed them during the captures.

MR, M1, M2 and M3 are ordinary matrix keys. They were expected to emit the mode event; they do not. Of the 122 keys, every one produced an f6 and none produced an event of another kind. The mode switch happens inside the keyboard, and the host only finds out from the f6 or by re-reading with 0x81.

Correction: (4,7) is brightness, not Timer

The documentation attributed f6 01 04 07 to the Timer key. The capture itself proves otherwise: each f6 (4,7) is followed 40 ms later by a brightness event, five times in a row, walking the levels 3, 2, 1, 0, 4. Timer is (4,8), which that document mentioned in passing as an "isolated pair". Two independent sources, and today's collection matches both.

The safe operating model

0x82 returns byte for byte what 0x02 wrote — across the 264 bytes the only field that differs is byte 3. Hence the procedure for the Linux tooling:

read the mode with 0x82 → change the desired byte → write it back with 0x02

There is no need to understand the fields still marked ? in order to touch the ones marked C: the unknown ones travel intact through the round-trip. And, since the M1/M2/M3 keys switch the mode with no software, re-read the active mode with 0x81 instead of assuming the last value written.

The three lighting toggles, and why two of them are no use

The documentation spoke of two toggles, 108 and 119. There are three: separating, across the 11 captures, the host's writes from the keyboard's answers, 107 behaves like a toggle too. And the app has exactly three keys, in sequence in the binary's configuration block: LightDisable, BacklightDisable, LightVolumeDisable. The count matches. C

119 = volume display, by elimination within the capture 03-config, whose exercised controls were polling rate (byte 8), repeat delay (which goes in 0x0A) and volume display — and 119 is the only toggle byte that moves there. C

107 and 108 are inert

Tested on hardware, each at 0 and at 1, in the static mode and in the mode with Wave running, with a mode switch on the keyboard itself between the steps. No change in any of the four combinations: the animation did not stop, nothing went dark.

The firmware accepts and stores them — a re-read returns the value written. It just does nothing with it. They are stored state, not control: probably the app's configuration living in the keyboard's memory so it travels with the device. It matches the original report that touching those toggles had no effect on Windows either. C

For the Linux tooling the consequence is a good one: preserve them through the round-trip and do not touch them — which is what read-change-write already does.

Byte 109: o Windows key lock

Found by accident, and the accident is the method. During the matrix collection the bag-symbol key was pressed, and i3's Win+E stopped working — the letter went through, the Win did not count as a modifier.

Comparing the active mode with a portrait taken before touching anything, a single byte of the 264 had changed: 109, from 00 to 01, and only in the active mode. Pressing the key again it went back and the Win came back with it. C

Two things close there: the bag key is the Windows key lock — the third of the column-4 trio, along with brightness (4,7) and timer (4,8) — and the lock is not done by zeroing the key in the assignment table: bytes 120–263 did not change. It is a flag of its own.

And it corrects the three RGB triples, which were shifted

The specification gave 109–117 as three RGB triples, "pure green from the factory". With 109 being the lock, the triples can only start at 110 — and read from there they are (255,0,0) three times: red, not green. The one-byte error was what shifted (255,0,0) into (0,255,0).

An independent confirmation: mode 1's LED matrix has 127 slots at exactly ff0000. The stored triple and the painted matrix agree.

The method is worth more than the finding. The byte came out of a diff, not of a sweep: there was a complete portrait taken before touching anything, and an observable change in behaviour. Comparing the two gave the exact byte, first time, without writing anything.

Key functions · bytes 120–263

One byte per slot, in the same order as the LED map — which confirms the map on hardware. The value is not fixed: it is the code of the function assigned to the key. From the factory each entry coincides with the key's own HID usage because nothing had been remapped. Assigning Ctrl to G6 changed byte 125 from 00 to e0; assigning a macro to G1 changed byte 120 to b4.

The nine types the KEY ASSIGNMENT dialog offers all write into the same byte. It works because the high ranges do not collide with the HID usages the keyboard uses (0x04–0x65, 0xE0–0xE7), so one byte is enough to address any function.

Disable writes 0x00; Default restores the native HID usage. Modifiers are ordinary keys: Ctrl is HID 0xE0, there is no modifier field.

And 0x00 really is silence, not "use the native one": with ScrLk's byte zeroed, the key stopped emitting entirely — two presses, no event —, while the untouched Pause showed up in the same listening window as a control. A key can be turned off in the keyboard's memory, with no service running. C

Text never reaches the keyboard

A Text's content does not appear on the wire, not even with "Save to Device Memory" — only the name goes. The consequence: a key with a Text function only works with G.SKILL's app running. It is not a capture gap, it is the product's design. C

0x0E and 0x0F: gradient per effect slot

On the wire, these two seemed to have two regularities that did not fit: a base every 71 bytes and values every 24. They do fit — the 24 was an artefact.

Sweeping FUN_100d5060 for the structural constants, only 23 appears, in a floating-point context: it is the gradient's interpolation. 24 does not exist in the function, so it could not be a real.

The function was later decompiled in full, and the layout deduced from the wire was confirmed — now with the channel bases pinned by the code, not by the shape of the packets. The builder settles three things the capture did not give:

The 23 is a ceiling, not a coincidence. The stop counter goes through if (n < 0x17) n++ — 0x17 = 23, the length of the channel. It is the same counter that bounds the filling loop and that is written at +0. So the header's first byte is the number of gradient stops, and the 03/04/06 values captured are counts. C

The effect color is quantized. Each stop comes out of ((comp × pct) / 100 >> 2) × 4: scaled by a percentage and rounded to a multiple of 4. Hence the ubiquitous fc — 252 is 255 at 100% — and the effect path never reaches ff, by construction. That is 6 effective bits per channel. C

The envelope, from a third source. The final stretch writes 7, then 0x0e or 0x0f, then <mode> + 1 into contiguous stack bytes — Report ID, command and 1-based mode. And it calls Sleep(500) after writing an effect. C

A slot is 71 bytes and the packet carries three, at 8, 79 and 150 — the three effect slots per mode, the same ones as subpages 02/05/08 of 0x0A. The slot used changes from packet to packet, which is how we know.

The “+24” was the sum of two things: the planar step of 23 plus a step of +1 in the index within the channel. The five captured packets have a value at channel 0 step 0, channel 1 step 1, channel 2 step 2 — the diagonal. In absolute offsets that gives 10, 34 and 58, a difference of 24, without a 24 existing anywhere. Five out of five packets decode that way. C

In other words: 0x0E and 0x0F carry a gradient, not per-key data. They are siblings of 0x08 — the same function builds all three — and not of 0x0B/0x12/0x15, which come out of FUN_100d7170 and are these:

Which effects have per-key data, and a confirmed prediction. After building the gradient, the caller only enters the FUN_100d7170 loop if the effect is 2, 3, 10 or 7 — and the loop runs 3 times. Against the helper table above, built from the capture and with no relation to this code: Ripple and Sonic with 0x0B ×3, Changeling 0x15 ×3, Rain 0x12 ×3, and nothing for Wave, Breathing and Cycle. Seven out of seven, including the three negatives — and the "×3" is the loop's count, not a coincidence with the R/G/B channels. C

Why the capture showed all zeros

The code has both branches, and the one that zeroes is explicit: when the effect is not in the per-key state, it does memset(buf+8, 0, 144) before sending. 0x08 · the rasterized gradient

69 data bytes (8–76) = 3 channels × 23 steps, planar: the effect's gradient interpolated step by step, cyclically — the last step wraps to the first, because the effect loops. Cut into lines of 23 from byte 8, a real packet aligns by itself into R, G and B. The values are quantized to 6 bits, stored shifted by 2.

Example of a 2-stop gradient, red at position 0 and blue at 100. G is zero across the 23 steps because there is no green in the gradient; R falls and rises again at the end, B does the mirror. Values in raw bytes, as they go out on the wire.

Bit 7: 1 = press, 0 = release. The low nibble carries the delay's high bits:

A single byte saturates at 2.55 s; with the extension the ceiling goes to ~41 s. Validated against a macro with an 8.65 s pause and another with Ctrl+C: events and delays match one for one what the app shows on screen. C

The UI does not allow mouse events inside a macro, only keys — a mouse function is a type of key assignment, a separate path. The macro's name goes by another path: 0x0A page 0x09, in ASCII.

0x85 · reading the macro C

It had never appeared in a capture: the official app was only ever seen writing macros. The command is in the confirmed read space and appears in the init and in the decompilation. Measured on 2026-10-17:

07 85 <mode> <index> <bank> 00 00 00

Two things came out of it. The macros from the Windows captures are still in the keyboard: mode 1 bank 1 returned the macro with the 8.65 s pause and mode 2 bank 1 the A B C, byte for byte — an independent validation of the decoder, months after the capture. And a never-written bank answers 0xFF, the same convention as 0x8A in the init; 0xFF means "there is nothing here" and is different from zeroed, which is an empty macro.

Two details for anyone implementing this: the answer comes back one byte short (263 of 264), so testing "all 256 are 0xFF" is never true — the header (FF FF against 00 01) is the test that works; and an immediate re-read after a write returns the old content, half a second later it returns the new one.

Initialization

28 packets in 3.2 s, from the 01-open capture. 0x16 is always the first message, and 0x0D appears as a begin/end pair around the writes. C

  1. 07 16 01 opens the session — and it is what turns f6 on
  2. 07 0d 00 enters configuration mode
  3. 07 8a 00 00..03 reads page 0 — all 0xFF
  4. 07 81 00 reads the active mode → 07 81 01
  5. 07 82 01 / 02 / 03 reads the information of the 3 modes
  6. 07 8a 1b/1c/1d … reads the modes' databases — all 0xFF
  7. 07 02 01 <256 B> rewrites mode 1 unchanged
  8. 07 0d 01 leaves configuration mode
  9. 07 07 00 15 command 0x07, role unknown
0x16 opens a session that nothing closes

Tested on hardware: the f6 event does not come by default. On a freshly power-cycled keyboard no key produces an event — until 0x16. That is why no capture showed who turns it on: on Windows the keyboard already came in turned on from an earlier run of the software, and in 01-open the first f6 events arrive 19 seconds before the app sends its own 0x16.

No command closes the session. Across the 11 captures 0x16 always appears as 07 16 01 and never with another argument; the official software does not close it even when it exits. And with the session open the keyboard may stop typing. What gives it back is a USB reset (dev.reset()), not 0x0D 01.

Any tool that sends 0x16 has to guarantee the reset on the way out, including on an exception and on a signal — and cannot count on Ctrl+C, which comes from the keyboard the test itself may knock out.

Why half the list now comes out on Linux

The Windows capture session could not settle 108 vs 119 for a structural reason: a capture only shows what the official UI does. If the software never exercises a field, it never appears on the wire.

On Linux the other half exists. Since 0x82 returns byte for byte what 0x02 wrote, it is possible to read the mode, change one byte, write it back and look at the keyboard. The items marked "settleable by experiment" become half an hour at the bench instead of reverse engineering.

And there is a cheaper route still, which has already produced a result: no writing needed at all. Take a portrait of the 3 modes, work the control on the keyboard itself, and compare. That is how byte 109 turned up — a single byte different out of 264, first time. It only works for what the keyboard can change on its own; for the rest, then yes, writing, with a backup and one byte at a time.
