The byte 0x07 is not a magic number

The abandoned repo legonigel/KM780-RGB-Linux-Driver calls byte 0 KM_START_CHAR, a "manufacturer magic character". It is the HID Report ID — the same 7 that makes up wValue = 0x0307, where 0x03 is the report type FEATURE and 0x07 the report ID. Anyone implementing the transport that way is right by accident and wrong the moment they generalize.

The transaction, the way the manufacturer does it

Taken from FUN_100d8fc0. The official software does not read the ACK on the interrupt endpoint 0x83: it writes, sleeps, and reads back into the same buffer. C

  1. memset(buf, 0, 0x200); buf[0]=0x07; buf[1]=cmd
  2. HidDevice_SetFeature(h, buf, 0x108, 0) ordinal 7
  3. Sleep(10) 50 ms on the paged commands
  4. HidDevice_GetFeature(h, buf, 0x108, 0) ordinal 8
  5. Sleep(10) 100 ms on the paged commands

The abandoned repo's ACK wait works, but it loops forever if the ACK never arrives — and it is not what the manufacturer does.

bcdDevice carries the firmware version

In the device descriptor, bcdDevice = 0x0077 is FW 77. A practical consequence: lsusb reveals the keyboard's firmware version with no software at all. The firmware also carries three copies of the configuration descriptor, identical except in the endpoints' bInterval — 1, 4 and 8 — which are the UI's polling rate options.

The event channel, 0x83

8 bytes, vendor page 0xFF00. This is where the keyboard speaks on its own: the MR/M1/M2/M3 keys switch the mode and record macros with no software, so the active mode changes underneath the host.

Command space

Bit 7 set = read. Confirmed empirically on six pairs (0x01/0x81, 0x02/0x82, 0x05/0x85, 0x09/0x89, 0x0A/0x8A, 0x12/0x92), no longer inferred. C

write observed read observed event device→host never seen on the wire
Do not sweep unknown commands

That is exactly what put the keyboard into bootloader mode: some byte between 0x96 and 0xAF is not a read, despite having bit 7 set. The "bit 7 means read" convention holds for the confirmed commands, not for arbitrary bytes. Recovery exists (FWUpdate.exe + the .hex), but it depends on a Windows machine.

The list is a floor, not the complete set. The scan of Setting.dll found 19 sites with an immediate command byte, but the binary has 37 push 0x108. The difference is sites that load the command from a register, out of the scan's reach — and that is what explains why 0x08, which the abandoned repo calls the "LED Effect Database", does not appear in it. ?

0x09 · LED Matrix Database

The color path. A complete update is three packets, one per channel — it is not key paging. Each packet carries 144 bytes, one per LED slot, with that channel's intensity on that LED.

Which channel is R, G and B

It could not be found out from the binary: the firmware treats the three channels symmetrically — FUN_000081b8 only clamps to 1..3 and copies 144 bytes — and each one comes from a distinct 4 KB bank in the external SPI flash (0x1070, 0x2070, 0x3070). A correspondence is a convention of the LED hardware, and it came out of a hardware test: F5 (slot 45) on channel 1 only, F6 (slot 54) on channel 2 only, F7 (slot 59) on channel 3 only, all with 0xFF. C

buf[3] = 1R · redF5 lit up red
buf[3] = 2G · greenF6 lit up green
buf[3] = 3B · blueF7 lit up blue

Three things the same test settled

There is no commit. The third packet closes the update; no separate apply command. 0x09 is authoritative for static color — in the test every other key went dark, because they were sent as zero; if there were an effect or brightness layer on top, they would have stayed lit. And the read is symmetric: 0x89 returns the bytes sent and echoes the header, which confirmed that buf[2] is the mode and buf[3] the channel.

The intensity is not here

It is byte 11 of the mode payload (0x02), with values 0 to 4 — the UI's five levels. Walking through all the levels, the only byte that varies across the 12 0x02 packets is 11, in the sequence 00 00 01 02 03 04, and the 0x09 packets sent alongside keep the color intact. That is: the firmware applies the brightness; the host does not pre-multiply the color. C

Key → LED slot map

There are 132 slots used out of 144. The order is not the keyboard's physical one — it is the hardware's LED scan order, which is obvious here: neighbouring slots land in opposite corners of the keyboard. Click a key to see the slot, o HID usage e o virtual-key code.

In the matrix, but not on the keyboard

Ten slots within the 132 have no physical key in the US/ABNT layout — they are positions from JIS/ABNT layouts and zones the matrix addresses but the board does not expose. The remaining 12 slots (144 − 132) are addressed by no table at all: they are always zeroed, so they simply do not exist.

The safe operating model

0x82 returns byte for byte what 0x02 wrote — across the 264 bytes the only field that differs is byte 3. Hence the procedure for the Linux tooling:

read the mode with 0x82 → change the desired byte → write it back with 0x02

There is no need to understand the fields still marked ? in order to touch the ones marked C: the unknown ones travel intact through the round-trip. And, since the M1/M2/M3 keys switch the mode with no software, re-read the active mode with 0x81 instead of assuming the last value written.

Key functions · bytes 120–263

One byte per slot, in the same order as the LED map — which confirms the map on hardware. The value is not fixed: it is the code of the function assigned to the key. From the factory each entry coincides with the key's own HID usage because nothing had been remapped. Assigning Ctrl to G6 changed byte 125 from 00 to e0; assigning a macro to G1 changed byte 120 to b4.

The nine types the KEY ASSIGNMENT dialog offers all write into the same byte. It works because the high ranges do not collide with the HID usages the keyboard uses (0x04–0x65, 0xE0–0xE7), so one byte is enough to address any function.

Disable writes 0x00; Default restores the native HID. Modifiers are ordinary keys: Ctrl is HID 0xE0, there is no modifier field.

Text never reaches the keyboard

A Text's content does not appear on the wire, not even with "Save to Device Memory" — only the name goes. The consequence: a key with a Text function only works with G.SKILL's app running. It is not a capture gap, it is the product's design. C

Animated effects

The active effect is byte 10 of the mode. The UI offers exactly 8 effects, all of them mapped; the IDs 0x05 and 0x06 do not exist in it. Each effect keeps its own duration: switching effect and coming back restores the previous value.

The 144 per-key bytes of 0x0B, 0x12 and 0x15

This was the biggest gap — the one the specification called impossible to settle by capture. It came out of decompiling FUN_100d7170, which builds all three commands in the same place.

Why the capture showed all zeros

The code has both branches, and the one that zeroes is explicit: when the effect is not in the per-key state, it does memset(buf+8, 0, 144) before sending. The official UI only applies a global effect, so the app sends a zeroed array. The field exists and is mapped; what is missing is a UI state that fills it — a limitation of the manufacturer's tool, not of the protocol.

0x08 · the rasterized gradient

69 data bytes (8–76) = 3 channels × 23 steps: the gradient of the gradient interpolated step by step, cyclically — the last step wraps to to the first, because the effect runs in a loop. The values are quantized in 6 bits, stored shifted by 2.

Example of a 2-stop gradient, red at position 0 and blue at 100. G is zero across the 23 steps because there is no green in the gradient; R falls and rises again at the end, B does the mirror. Values in raw bytes, as they go out on the wire.

0x05 · macro content

Sent in three banks: buf[2] = mode, buf[3] = 0x00, buf[4] = 1, 2, 3. After a 00 01 header in bytes 8–9 come 3-byte records.

Bit 7: 1 = press, 0 = release. The low nibble carries the delay's high bits:

delay = ((flag & 0x0F) << 8) | delay_byte   × 10 ms

A single byte saturates at 2.55 s; with the extension the ceiling goes to ~41 s. Validated against a macro with an 8.65 s pause and another with Ctrl+C: events and delays match one for one what the app shows on screen. C

The UI does not allow mouse events inside a macro, only keys — a mouse function is a type of key assignment, a separate path. The macro's name goes by another path: 0x0A page 0x09, in ASCII.

Initialization

28 packets in 3.2 s, from the 01-open capture. 0x16 is always the first message, and 0x0D appears as a begin/end pair around the writes. C

  1. 07 16 01 opens the session
  2. 07 0d 00 enters configuration mode
  3. 07 8a 00 00..03 reads page 0 — all 0xFF
  4. 07 81 00 reads the active mode → 07 81 01
  5. 07 82 01 / 02 / 03 reads the information of the 3 modes
  6. 07 8a 1b/1c/1d … reads the modes' databases — all 0xFF
  7. 07 02 01 <256 B> rewrites mode 1 unchanged
  8. 07 0d 01 leaves configuration mode
  9. 07 07 00 15 command 0x07, role unknown
